Цель (одно предложение):
Разработать генератор иммерсивного театра, обеспечивающий сценарное ветвление по результатам голосования зрителей и нейросетевую генерацию продолжения, интегрированную с серверным API, хранилищем сценарных артефактов и информационной подсистемой (настольный клиент сотрудников, мобильный клиент зрителя, реляционная СУБД, защищённый контур доступа).

Задачи (нумерованный список, соответствует введению диплома):
1. Провести анализ предметной области иммерсивного театра (вариативный сценарий, голосование зрителей).
2. Выполнить обзор существующих решений: ИС культурных учреждений, подходы к генерации и оркестрации (n8n и аналоги), публикация API по HTTP.

5. Развернуть рабочую область n8n с нейросетевым этапом (контекст сцены и выбранный вариант).
6. Реализовать серверную часть: артефакты, голосования, аутентификация, авторизация, интеграция.
7. Реализовать настольный и мобильный клиенты.

Слайд 4.3. Диаграмма последовательности (UML Sequence)
--------------------------------------------------------------------------------

Цель:
Показать обмен сообщениями на одном ключевом процессе. Рекомендуемый сценарий для вашей темы:
«Запуск обработки ТЗ сценария через вебхук n8n» или «Голосование зрителя → передача выбора → запись → подготовка контекста для генерации».

Участники (линии жизни):
Сотрудник (сценарист) | Настольный клиент (PySide6) | API (FastAPI) | Файловое хранилище | n8n | Нейросетевой провайдер (внутри n8n, опционально пятая линия)

Упрощённая расшифровка шагов (подписи к стрелкам):
1. Выбор сценария → «Запустить обработку».
2. Клиент → API: POST с токеном (Authorization).
3. API: проверка роли, чтение файла ТЗ с диска.
4. API → n8n: HTTP POST (multipart), тайм-аут увеличен.
5. n8n → модель: запрос генерации; ответ возвращается в n8n.
6. n8n → API: тело результата (и при необходимости имя файла в заголовке).
7. API: запись результата, обновление статуса конвейера в БД.
8. API → клиент: успех / код ошибки при недоступности n8n.

Акцент для комиссии:
«Диаграмма показывает не только таблицы, но и реальный сетевой контур с вынесенным оркестратором и устойчивостью при сбоях внешней интеграции.»

Итоговый абзац для пунктов 4.1–4.3 (можно озвучить при переходе к следующему разделу):
«Представлены модели предметной области: варианты использования задают роли и функции, ER-диаграмма — структуру данных театра и сценарного артефакта, диаграмма последовательности — взаимодействие клиента, API, хранилища и n8n при обработке ТЗ. Это определило модульность реализации и контракт вебхука.»

5. ОБЗОР СУЩЕСТВУЮЩИХ РЕШЕНИЙ / ТЕОРЕТИЧЕСКАЯ ОСНОВА
================================================================================

Структура слайда: таблица «группа решений — сильные стороны — ограничение для данного проекта».

Строки (из главы 1.5 диплома):
1. ИС для культурных учрежств и билетно-репертуарные системы — сильны в учёте репертуара; как правило, нет контура «ТЗ → нейросеть → артефакт в карточке сценария».
2. Универсальные чаты с LLM — быстрый старт; нет единого контура с ролями сценарист/зритель, трассируемости и связи с показом.
3. Прямой вызов API LLM из кода приложения — вся логика в репозитории; тяжёлая смена провайдера, промпта, повторов.
4. Оркестраторы (n8n и аналоги) — визуальная сборка конвейера, вебхук, вынос интеграций из ядра API.
5. MLOps-платформы — избыточны для сценария «вебхук + один тип документа» в рамках ВКР.

Критерии сравнения (столбцы таблицы):
учёт репертуара и площадок | встраивание сценарного ТЗ | эволюция нейросетевого шага | мобильный сервис зрителя | контроль доступа и секреты

Вывод слайда:
«Готовое коробочное решение не закрывает целевую связку: прикладная ИС + мобильный зритель + n8n как контур генерации. Поэтому обоснована разработка собственного комплекса с открытым контрактом вебхука и реляционным хранилищем.»

6. ПРЕДЛАГАЕМОЕ РЕШЕНИЕ / АРХИТЕКТУРА
================================================================================
Три уровня подачи: контейнеры (крупные блоки) → внутренняя структура API → ключевой сценарий (алгоритм) + безопасность.

--------------------------------------------------------------------------------
Слайд 6.1. Высокоуровневая архитектура (развёртывание / C4 Containers)
--------------------------------------------------------------------------------

Узлы (адаптация под ваш проект):
1. Рабочее место сотрудника: настольное приложение (PySide6) → HTTPS → API.
2. Мобильное устройство зрителя: Android-приложение (Kotlin, Jetpack Compose) → публичные маршруты API.
3. Сервер приложений: FastAPI (ASGI, uvicorn), бизнес-логика, JWT, вызов n8n (requests/httpx с тайм-аутом).
4. PostgreSQL: транзакционное хранение учётных и предметных данных.
5. Файловый каталог на сервере: ТЗ и результаты генерации.
6. Отдельный сервис: n8n (вебхук), вне репозитория API; опционально контейнеры Docker Compose для API и СУБД.

Подпись к стрелке API ↔ n8n:
«Инициирование конвейера обработки; при отсутствии URL вебхука обработка не запускается (режим без внешней интеграции).»

Тезис:
«Архитектура многоуровневая: клиенты не обращаются к БД напрямую; нейросетевая логика не зашита в монолит, а вынесена в настраиваемую рабочую область n8n.»

--------------------------------------------------------------------------------
Слайд 6.2. Внутренняя структура серверной части (слои / компоненты)
--------------------------------------------------------------------------------

Слои (пример для слайда):
— Маршруты REST, схемы Pydantic, зависимости (токен, сессия БД).
— Сервисы / CRUD-слой предметной области, оркестрация вызова n8n, работа с файлами.
— SQLAlchemy ORM, модели таблиц, миграции / скрипты схемы.
— Сквозные: хеширование паролей (bcrypt), логирование, обработка ошибок интеграции.

Стрелки зависимостей:
«Маршруты → бизнес-операции → доступ к данным; политики ролей проверяются до выполнения операции.»

--------------------------------------------------------------------------------
Слайд 6.3. Ключевой сценарий / алгоритм (блок-схема или Activity)
--------------------------------------------------------------------------------

Рекомендуемый сценарий: «Обработка ТЗ и запись результата» или «Учёт голосования и передача контекста для генерации следующей ветки».

Шаги (адаптируйте под код):
Начало → Проверка: настроен ли вебхук n8n? Если нет — возврат пользователю сообщения об недоступности конвейера.
Если да — установить статус конвейера «ожидание/выполнение» → отправить файл в n8n → ожидание ответа с тайм-аутом.
Ветка ошибка сети / код ответа вне успеха: зафиксировать статус ошибки, не перезаписывать корректные данные без явной операции.
Успех: сохранить тело ответа в файл, обновить метаданные, статус «готово» → Конец.

Коротко для устной части:
«Это центральный операционный сценарий диплома: прозрачные состояния конвейера и корректное поведение при недоступности оркестратора.»

--------------------------------------------------------------------------------
Слайд 6.4. Данные и безопасность (фрагмент ERD + потоки защиты)
--------------------------------------------------------------------------------

Слева: Users, Roles, при необходимости связь с Employee; хранение только хешей паролей.

Справа поток:
Клиент — HTTPS → API; выдача JWT; последующие запросы с Authorization; разграничение маршрутов сотрудник / публичный зритель; секреты и URL n8n только из переменных окружения.

Итоговый абзац для раздела 6 (озвучка):
