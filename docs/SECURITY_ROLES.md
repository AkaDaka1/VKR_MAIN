# Модель доступа и роли

## Аутентификация и JWT

- Вход: `POST /token` (OAuth2 password form), ответ содержит `access_token`.
- Клиент сохраняет токен в `app/api_session.py`; все запросы репозиториев идут с заголовком `Authorization: Bearer …` (`backend/http_client.py`).
- `GET /users/me` и все прочие операции (кроме `/token`) требуют валидный JWT и известную роль из каталога `app/roles.py`.

## Каталог ролей (поле `Employee.role`)

| Слаг | Описание |
|------|----------|
| `admin` | Администратор: полный доступ. |
| `manager` | Менеджер: операционные данные (театры, залы, показы, билеты, клиенты, оборудование, услуги, аренда, голоса), франшизы; просмотр сотрудников; **без** управления учётными записями. |
| `scenarist` | Сценарист: сценарии, акты, части (чтение остального по API при необходимости контекста). |
| `franchise_partner` | Партнёр по франшизе: только чтение через API (как у любой аутентифицированной роли на GET); изменения в UI отключены. |
| `user` | Базовый пользователь: чтение; изменения в UI отключены. |

Правила на сервере задаются в `api/api.py` через `api/rbac.py`. Клиент дублирует ограничения в `MainWindow._apply_role_restrictions` и функциях `app/roles.py` (`can_mutate_entity`, `can_open_query`, …).

## Сотрудники (особый случай)

- Просмотр списка сотрудников: **admin**, **manager**.
- Создание / изменение / удаление сотрудников: только **admin**.

## Защита в UI

- Нельзя удалить учётную запись, совпадающую с текущим пользователем.

## Миграция БД

- Поле `Employee.role` расширено до `String(64)` в модели. Для существующей PostgreSQL-таблицы при необходимости выполните:
  `ALTER TABLE "Employee" ALTER COLUMN role TYPE VARCHAR(64);`

## Продакшен

- Секреты только в окружении; HTTPS для API; не коммитить `.env` с реальными паролями.
